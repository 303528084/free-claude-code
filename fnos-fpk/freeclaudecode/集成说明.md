# Free Claude Code 汉化版 · 飞牛 FPK 骨架（原生 + 统一网关）

按 `developer.fnnas.com` 官方模型搭的包结构：**Native 应用 + 统一网关入口**（不是 Docker 形式）。
结构、字段、脚本都是照着知识库里的 Native 案例、Manifest、应用入口、应用资源、环境变量、图标几篇来的。

## 关键取值

| 项 | 值 | 依据 |
| --- | --- | --- |
| appname | `freeclaudecode` | 全局唯一，入口 ID 前缀也用它 |
| 入口类型 | `iframe` + `gatewayPrefix=/app/freeclaudecode` + `gatewaySocket=fcc.sock` | Native 案例 |

## 打包与安装

**先装配载荷（必须在 Linux 上做，NAS 本机最快）**。`app/venv` 里的绝对路径要和安装后的
`/var/apps/freeclaudecode/app` 对齐，所以脚本会把 prefix 直接烧成生产路径：

```bash
cd /vol1/1000/tmp/fnos-fpk            # 包目录的上一级
sudo bash freeclaudecode/scripts/build_payload.sh
```

它做三件事：编译 CPython 3.14.10（prefix 已烧死）、建 venv 并从我们 Release 装 `+zh.1` wheel、
把 `runtime/` 与 `venv/` 拷回包目录并瘦身。

**再打包**（fnpack 有 Windows x86 / Linux x86 版本，机器上能跑哪个就用哪个）：

```powershell
fnpack build --directory .\freeclaudecode
```

打包前 `fnpack` 会检查：`manifest`、`config/privilege`、`config/resource`、`ICON.PNG`、`ICON_256.PNG`、
`app/`、`cmd/`、`wizard/`、以及 `desktop_uidir` 指向的 `app/ui/`。这些都已在骨架里放好了。

装到 NAS 后先看三处：

1. 应用中心 → 我的应用 → 状态是“运行中”（`cmd/main status` 返回 0）；
2. 日志：`/vol<x>/@appdata/freeclaudecode/app.log`（即 `${TRIM_PKGVAR}/app.log`）；
3. 桌面图标点开是否显示 Admin 页面（这一步的机制见下面的第 2、3 点）。

## 三个硬点的现状（2026-11-20 实测）

| # | 硬点 | 现状 |
| --- | --- | --- |
| 1 | uvicorn 没有 UDS | 用 shim 承接（已实跑通过，见下） |
| 2 | Admin 用绝对 `/admin` 路径，挂前缀后 404 | **shim 在响应体里改写，已实测通过，项目代码零改动** |
| 3 | Admin 的 loopback 校验拦 NAS 域名 | **shim 改写 Host/Origin，已实测通过，项目代码零改动** |


### 1. socket 从哪来：uvicorn 只支持 host/port

`src/free_claude_code/cli/commands.py` 里构造的是 `uvicorn.Config(app, host=settings.host, port=settings.port, …)`，
没有 `uds` 参数。统一网关只会往 `${TRIM_APPDEST}/fcc.sock` 写请求，所以有两条路：

- **路线 A（推荐，改 fork）**：给 settings 加一个 socket 路径配置，`uvicorn.Config(..., uds=...)`；
  改动约十几行，无额外进程，性能最好。顺带把 `root_path` 一起加上（见下面第 2 点）。
- **路线 B（不改代码，用 shim）**：`app/shim/gateway_shim.py` 已写好并在 `cmd/main` 里拉起。
  它监听 socket、剥掉 `/app/freeclaudecode` 前缀、把 `Host`/`Origin` 改写成 `127.0.0.1:8586` 再转发到
  fcc 的 TCP 端口。零改动可用，但每个连接只处理一个请求、不支持 chunked 请求体。

### 2. 路径前缀：已由 shim 在响应体里改写解决（实测通过，不改项目代码）

问题本来是这样的：网关前缀是 `/app/freeclaudecode`，而 fcc 的 Admin 用的是**绝对路径**——

- `admin_static/index.html` 12 处绝对引用：`/admin/assets/__FCC_VERSION__/admin.css`、`admin.js`、`app-icon.svg`…；
- `admin_static/admin.js` 21 处绝对调用：`/admin/api/status`、`/admin/api/config`、`/admin/api/providers/...`。

在 iframe 里浏览器会把这些解析成 `http(s)://NAS域名/admin/...`，绕出网关前缀 → 404。

shim 的处理办法：转发响应时，若 `Content-Type` 属于 HTML / JS / CSS / JSON 且带 `Content-Length`，
就在响应体里把 `/admin` 路径替换成 `/app/freeclaudecode/admin`。两个关键细节：

1. **边界正则**：只改「`/admin` 后面紧跟 `/`、`"`、`'`、反引号、`\`、`?`、`#`、空白、`<` 或行尾」的情况。
   第一版用无边界替换，把 `/admin.css`、`/admin.js` 这几个**文件名**也改坏了（实测发现并修正）。
2. **去掉 Accept-Encoding**：转发时删除该请求头，逼上游返回未压缩响应，改写才能在明文上生效。
   代价是网关内这一段不压缩（本机回环，无所谓）。

实测结果（云主机上真实跑 fcc-server 3.14.10 + 本 shim，走 Unix Socket 模拟网关）：

| 请求 | 结果 |
| --- | --- |
| 直连 `/admin`，`Host: nas.example.com` | 403（原行为，保留） |
| 经 socket `/app/freeclaudecode/admin` | 200 |
| 经 socket 取 `admin.css` / `admin.js` / `app-icon.svg` | 200 / 200 / 200 |
| 经 socket 调 `/admin/api/status` | 200 |
| 页面里资源路径 | 已变成 `/app/freeclaudecode/admin/assets/6.19.40+zh.1/admin.css`，文件名未被误改 |
| `admin.js` 里的接口路径 | 已变成 `"/app/freeclaudecode/admin/api/status"` |

限制：chunked 响应（没有 `Content-Length`）只做流式透传、不改写。Admin 的静态资源和 JSON 接口都带
`Content-Length`，实测全部命中；SSE 走流式分支，不受影响。

> 长期正解仍是给 fork 加 `root_path` + 前端相对路径（见路线 A）。shim 这条是按你"先不改代码"的决定先跑通。

### 3. loopback 校验：已由 shim 改写 Host/Origin 解决（实测通过，不改项目代码）

`api/admin_security.py::require_loopback_admin` 三重校验：`client.host`、`Host` 头、`Origin` 头都必须是回环。

- `client.host`：网关在本机转发，本来就是回环，能过；
- `Host`：原本是 NAS 域名 → **403**（实测确认）；
- `Origin`：POST 时是 `http(s)://NAS域名` → **403**（实测确认）。

shim 把这两个头改写成 `Host: 127.0.0.1:8586` / `Origin: http://127.0.0.1:8586`，三重校验自然通过，
实测 `/admin`、`/admin/assets/*`、`/admin/api/status` 全部 200。

需要清楚代价：这样 fcc 无法区分「网关转发」和「本机进程」，Admin 的准入边界退化为
「谁能写这个 socket 谁就能进」。缓解因素是 socket 在 `${TRIM_APPDEST}`（只有 package 用户和 root 可写，
shim 自己 `chmod 0660`），且网关入口本身是 `allUsers=false` + 已登录管理员。

以后想更严，再把「带可信 `X-Trim-Isadmin: true` 才放行」的分支加进 `require_loopback_admin`——
那时才需要动代码，现在不必。

## 端口与客户端接入

`manifest.service_port=8586`，`cmd/main` 用它作为 `PORT`：

- 局域网里的 Claude Code / Codex：`http://NAS地址:8586`（Anthropic 风格用根路径，OpenAI 风格走 `/v1`），
  `Authorization: Bearer <安装时设置的令牌>`；
- 是否允许绑定到 `0.0.0.0` 由安装向导的「允许局域网客户端直连」开关决定，写在 `${TRIM_PKGETC}/fcc.env`；
- Admin 永远不走这个端口（Host/Origin 校验会 403），只走网关。

## 仍然存在的风险（真机才会暴露）

1. 网关到底把什么路径交给 socket（`/app/freeclaudecode/admin` 还是别的前缀组合）——现在按
   `gatewayPrefix + url` 推断，真机上用 `tail -f ${TRIM_PKGVAR}/shim.log` 一看就清楚，必要时调
   `cmd/main` 里 shim 的 `--prefix`。
2. `X-Trim-*` 头在 POST 里是否稳定下发——不影响 Admin 能用（shim 不依赖它），只影响以后做更严的校验。
3. 首次启动时 fcc 会在 `~/.fcc` 建配置；如果 package 用户的 HOME 不可写，需要把 `HOME` 指到
   `${TRIM_PKGVAR}/home`（`cmd/main` 里已按这个思路设了，真机确认一次）。
